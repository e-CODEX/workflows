## SAST

### SonarCloud Java Analysis

This workflow runs a SonarCloud analysis on a Java project. It requires the following inputs:

#### SonarCloud Usage

```yaml
on:
  push:
  pull_request:
    types: [opened, synchronize, reopened]
jobs:
  sonar:
    uses: e-CODEX/workflows/.github/workflows/sonar-java.yaml@main
    with:
        jacoco-xml-report-path: 'target/site/jacoco/jacoco.xml'
        java-version: 21
        build-tool: 'maven'
    secrets: inherit
```

| Name                     | Description                                                     | Required | Default |
| ------------------------ | --------------------------------------------------------------- | -------- | ------- |
| `jacoco-xml-report-path` | Path to the coverage report generated by JaCoCo                 | No       | -       |
| `java-version`           | Java version to use for the analysis. Must be 17 or higher      | Yes      | 21      |
| `build-tool`             | Build tool to use for the analysis. Must be 'maven' or 'gradle' | Yes      | 'maven' |

> [!IMPORTANT]
> Building with Gradle requires the use of the Gradle wrapper.

> [!TIP]
> Using jacoco-xml-report-path with multi module can be problematic.

It also requires the following secret:

| Name          | Description      | Required |
| ------------- | ---------------- | -------- |
| `SONAR_TOKEN` | SonarCloud token | Yes      |

## CI/CD

### Java CI with Maven

This workflow tests a Java project using Maven on multiple operating systems, and creates and publishes a Software Bill of Materials (SBOM) file.
It assumes that the `verify` goal runs the tests, and the `package` goal creates the artifacts as well as a sbom file.

#### Maven CI Usage

```yaml
on:
  push:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  CI:
    uses: e-CODEX/workflows/.github/workflows/maven-ci.yaml@main
    with:
      java-version: 21
      maven-parameters: '-Djacoco.skip=true'
      sbom-path: 'target/bom.xml'
      artifact-path: 'target/*.jar'
              
```

It requires the following inputs:

| Name               | Description                                                      | Required | Default |
| ------------------ | ---------------------------------------------------------------- | -------- | ------- |
| `java-version`     | Java version to use for the build. Tests are run on LTS versions | Yes      | 21      |
| `maven-parameters` | Extra parameters to pass to Maven                                | No       | -       |
| `sbom-path`        | Path to the SBOM file generated by the build                     | Yes      | -       |
| `artifact-path`    | Path to the artifact generated by the build                      | Yes      | -       |

### Docker Build and Push

This workflow builds and publishes Docker images to the e-CODEX JFrog registry, following SemVer and GitFlow conventions.
Every step is commented in the workflow file. In short:

- **Login:** GitHub OIDC is exchanged by `setup-jfrog-cli` for a short-lived JFrog token. No secrets are stored.
- **Build-info:** the image is recorded in the JFrog build-info `<repository>-docker` (`jf rt build-docker-create`).
- **SBOM and provenance in the image:** BuildKit generates an SPDX SBOM and a SLSA provenance (`mode=max`) and stores
  them in the image index.
- **GitHub provenance attestation, in two forms:**
  1. pushed to the registry as an OCI referrer of the image, for registry-only tools (`cosign`, `oras`,
     `gh attestation verify --bundle-from-oci`);
  2. with subject `oci://<registry>/<image>`, which `setup-jfrog-cli` attaches to the image in Artifactory as JFrog evidence.

  Two attestations are needed because `actions/attest` can only push to a registry with a plain image name, while JFrog
  only recognises an `oci://` subject. At the end of the job, the `setup-jfrog-cli` post step tries to create evidence
  from every attestation, so it logs one expected warning for the first one.
- **End of job:** `setup-jfrog-cli` publishes the build-info and creates the evidence.

#### Docker Build Usage

```yaml
jobs:
  docker:
    permissions:
      contents: read
      id-token: write
      attestations: write
    uses: e-CODEX/workflows/.github/workflows/docker-build-push.yaml@main
    with:
      image-name: 'my-application'
      environment: 'production'
      registry: 'scm.ecodex.eu/docker'
```

| Name            | Description                                                                           | Required | Default                |
| --------------- | ------------------------------------------------------------------------------------- | -------- | ---------------------- |
| `image-name`    | The name of the Docker image to build and push                                        | Yes      | -                      |
| `tag`           | The tag to checkout (required with `refresh`)                                         | No       | -                      |
| `environment`   | Deployment environment                                                                | No       | 'development'          |
| `registry`      | Docker registry to push images to (`<host>/<artifactory-repository>`)                 | No       | 'scm.ecodex.eu/docker' |
| `refresh`       | Rebuild the released `tag` with fresh base images and no cache, overwriting its image | No       | false                  |
| `floating-tags` | Refresh only: also move `<major>.<minor>` and `<major>`                               | No       | false                  |
| `latest`        | Refresh only: also move `latest`                                                      | No       | false                  |

> [!NOTE]
> The workflow generates the tags `edge` (develop), `latest` + `1.2.3`, `1.2`, `1` (releases) and the short SHA.

#### Refreshing a released image (security fixes without a new release)

With `refresh: true` the image of the released `tag` is rebuilt from that git tag with `--pull --no-cache`
(newest base image and OS packages, same application source) and pushed over the existing `1.2.3` tag.
`1.2`, `1` and `latest` are only moved when `floating-tags` / `latest` are set, so an old release line never takes
over the tags of a newer one. The OIDC identity needs *Delete/Overwrite* permission on the Docker repository.

```yaml
on:
  workflow_dispatch:
    inputs:
      tag:
        required: true
        type: string
jobs:
  refresh:
    permissions:
      contents: read
      id-token: write
      attestations: write
    uses: e-CODEX/workflows/.github/workflows/docker-build-push.yaml@main
    with:
      image-name: 'my-application'
      tag: ${{ inputs.tag }}
      refresh: true
      environment: 'production'
```

### JFrog CLI publishing, SBOMs and attestations

The Maven and Gradle publish workflows deploy with the JFrog CLI (`jf mvn deploy` / `jf gradle artifactoryPublish`),
authenticated with GitHub OIDC through `jfrog/setup-jfrog-cli`. Every step is commented in the workflow files. In short:

- **Deployment and build-info:** all artifacts and the resolved dependencies are recorded in the JFrog build-info
  `<repository>` (releases) or `<repository>-snapshot`.
- **SBOM:** the CycloneDX SBOM is deployed with the artifacts. Maven: attached by `cyclonedx-maven-plugin`. Gradle:
  uploaded next to the distribution as `<distribution>-cyclonedx.json`.
- **Attestations:** the main artifact (`distribution-path`, the distribution zip) gets a SLSA build-provenance
  attestation and an SBOM attestation. Both are signed with Sigstore and stored in GitHub. Their subject is the zip's path
  in Artifactory, which is looked up by sha256 because the deployed name differs from the local one.
- **End of job:** `setup-jfrog-cli` adds the git details, publishes the build-info and attaches both attestations to
  the zip as JFrog evidence. Evidence needs the JFrog Evidence service; without it the post step only logs a warning.

Callers must grant `id-token: write` and `attestations: write` (and `contents: write` for dependency submission).
New inputs: `deploy-repo`, `distribution-path` (required), `sbom-path`. `maven-repo-id` is deprecated and ignored.

### Maven Snapshot Publish to Repository

This workflow publishes a Maven snapshot to a JFrog Maven repository with `jf mvn deploy` (see [JFrog CLI publishing](#jfrog-cli-publishing-sboms-and-attestations)).
The deployment repository is given with `deploy-repo` (default `ecodex-snapshots`); `distributionManagement` credentials are not needed.

#### Maven Snapshot Usage

```yaml
on:
  push:
    branches:
      - develop
jobs:
  publish:
    uses: e-CODEX/workflows/.github/workflows/maven-publish-snapshot.yaml@main
    with:
      java-version: 21
      maven-parameters: '-Pproduction'
      deploy-repo: 'ecodex-snapshots'
      distribution-path: 'domibusConnectorDistribution/target/domibusConnector.zip'
```

It requires the following inputs:

| Name               | Description                        | Required | Default |
| ------------------ | ---------------------------------- | -------- | ------- |
| `java-version`     | Java version to use for the build. | Yes      | 21      |
| `maven-parameters` | Extra parameters to pass to Maven  | No       | -       |
| `deploy-repo`      | Artifactory deployment repository  | No       | 'ecodex-snapshots' / 'ecodex-releases' |
| `distribution-path` | Local path of the distribution zip to attest | Yes | - |
| `sbom-path`        | Path of the aggregated CycloneDX JSON SBOM | No | 'target/bom.json' |
| `maven-repo-id`    | Deprecated, ignored                | No       | -       |

#### Maven Release Usage

```yaml
on:
  push:
    branches:
      - main
jobs:
  publish:
    steps:
      - name: Check the current release version
        uses: e-CODEX/workflows/.github/workflows/maven-validate-release-version.yaml@main
        
      - name: Tag the current release version
        uses: e-CODEX/workflows/.github/workflows/maven-tag-release-version .yaml@main
        
      - name: Publish the current release version
        uses: e-CODEX/workflows/.github/workflows/maven-publish-release.yaml@main
        with:
            java-version: 21
            deploy-repo: 'ecodex-releases'
            distribution-path: 'domibusConnectorDistribution/target/domibusConnector.zip'
        
```

It requires the following inputs:

| Name               | Description                        | Required | Default |
| ------------------ | ---------------------------------- | -------- | ------- |
| `java-version`     | Java version to use for the build. | Yes      | 21      |
| `maven-parameters` | Extra parameters to pass to Maven  | No       | -       |
| `deploy-repo`      | Artifactory deployment repository  | No       | 'ecodex-snapshots' / 'ecodex-releases' |
| `distribution-path` | Local path of the distribution zip to attest | Yes | - |
| `sbom-path`        | Path of the aggregated CycloneDX JSON SBOM | No | 'target/bom.json' |
| `maven-repo-id`    | Deprecated, ignored                | No       | -       |
